# Duplicated Or Overlapping Logic

| Concept | Files involved | What is duplicated or overlapping | Best source of truth | What should consume it | Suggested cleanup | Priority |
|---|---|---|---|---|---|---|
| Cloud cover / rain / humidity | `RegionAtmosphereState`, `WeatherSnapshot`, `AtmosphereClientState`, `AtmosphereFogState`, `ServerWeatherStateResolver`, `WeatherSampler`, `SimpleCloudsWhiteoutFogHandler` | The same weather intensity ideas appear in backend state, client smoothing, and fog composition | `RegionAtmosphereState` plus a future render snapshot | Client cache, renderer, fog system | Define one backend weather contract and derive visual values from it | High |
| Wind vectors / wind forecasts | `WindEngine`, `WindRuntimeState`, `WindVector`, `WindForecast`, `WeatherSnapshot`, `TornadoInstance`, `HurricaneInstance` | Wind is represented as model data, forecast data, and storm behavior inputs | `WindEngine` and `WindVector` | Storm systems and future render snapshots | Keep wind authority backend-owned and render consumers read-only | High |
| Storm lifecycle data | `TornadoManager`, `TornadoInstance`, `TornadoSnapshot`, `HurricaneManager`, `HurricaneInstance`, `HurricaneSnapshot`, `SyncTornadoesPacket`, `SyncHurricaneStatePacket` | Similar lifecycle concepts are repeated across managers, instances, snapshots, and packets | Snapshot objects plus the manager that owns live state | Client caches and renderers | Make the snapshot boundary the only render-facing source of truth | High |
| Simple Clouds cloud mapping | `CloudLibrary`, `WeatherType`, `SimpleCloudSpawner`, `SimpleCloudsCompat`, `src/main/resources/data/simpleclouds/cloud_types/*`, `src/main/resources/data/simpleclouds/cloud_spawning/*` | Cloud IDs, weather categories, and spawn policies are spread across code and resources | Resource definitions plus a single mapping helper | Spawners and compatibility adapters | Document the cloud-id mapping rules and stop duplicating category logic later | Medium |
| Client smoothing / cached view state | `AtmosphereClientState`, `AtmosphereFogState`, `ClientHurricaneStateCache`, `TornadoRenderDebugState`, `ClientTickHandler` | Several systems smooth or stage the same visible data in different ways | A future `CloudRenderStateCache` concept | Renderers and HUD effects | Consolidate view-state ownership after the renderer contract exists | High |
| Region lookup and forecast access | `ForecastOrchestrator`, `ForecastGenerator`, `RegionForecastOrchestrator`, `WeatherSampler`, `AtmosphericStateRegistry`, `RegionAtmosphereState` | Multiple layers can answer “what is the weather here?” in slightly different ways | Region climate state + forecast orchestrator | Simulation and compatibility layers | Separate forecast generation from live lookup more explicitly | Medium |
| Render snapshot style data | `HurricaneRenderSnapshot`, `HurricaneRenderDescriptor`, `HurricaneCloudVolume`, `TornadoSnapshot`, `TornadoInstance` | Render-facing data exists in multiple shapes and levels of abstraction | Dedicated snapshot records | Renderers and compatibility hooks | Keep render data immutable and document what is derived vs authoritative | Medium |
| Lighting / fog darkening | `AtmosphereFogState`, `SimpleCloudsWhiteoutFogHandler`, shader files in `resources/assets/projectatmosphere/shaders/core/*` | Lighting and fog color decisions are split between Java and shader assets | A future lighting/fog snapshot contract | Renderers and shaders | Create one documented lighting contract before adding cloud shadows | High |
