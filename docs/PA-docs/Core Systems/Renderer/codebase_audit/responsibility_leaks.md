# Responsibility Leaks

| File / class | Leak type | Why it is a problem | Impact on future cloud renderer | Suggested cleanup | Priority | Risk |
|---|---|---|---|---|---|---|
| `manager/AtmosphereManager.java` | Server lifecycle + sync + regen + cloud queueing | It is a global coordinator with too many unrelated tasks | Makes it harder to find where cloud render data should be sourced | Split orchestration concerns into smaller boundary objects later | High | High |
| `manager/ForecastOrchestrator.java` | Storage + runtime + login sync + rebuild policy | It hides several ownership layers inside one service | A future render snapshot could accidentally depend on forecast internals | Move toward a narrower runtime coordinator and documented source-of-truth boundaries | High | High |
| `modules/atmosphere/CloudManager.java` | Simulation + region scanning + spawn policy + telemetry | This mixes real atmosphere updates with cloud lifecycle control | Cloud renderer inputs become harder to reason about | Separate state application from spawning/telemetry later | High | High |
| `manager/SimpleCloudSpawner.java` | Weather sampling + cloud selection + spawn search | It owns policy and discovery, not just spawning | Future renderer-facing cloud ids may depend on hidden heuristics | Extract a cleaner spawn strategy boundary later | High | High |
| `compat/SimpleCloudsCompat.java` | Adapter + radius policy + wind coupling + cloud creation | Compatibility code is carrying gameplay policy | Renderer integration points will be hard to isolate | Reduce to a thin adapter when the render boundary is stable | High | High |
| `modules/tornado/TornadoManager.java` | Simulation + persistence + snapshot sync + cloud attachment | Too many responsibilities for one manager | Future cloud renderer state could become coupled to storm lifecycle code | Introduce dedicated snapshot/cache boundaries later | High | High |
| `modules/tornado/TornadoInstance.java` | Simulation + movement + destruction + render fields | Instance data and visual concerns are mixed | Hard to tell what the renderer is allowed to read | Pull render-only data into a future render state object | High | High |
| `modules/hurricane/HurricaneManager.java` | Simulation + sync + persistence + debug + atmosphere interaction | Broad storm orchestration with debug concerns mixed in | Difficult to define a clean render state contract | Separate runtime, debug, and render coordination later | High | High |
| `modules/hurricane/HurricaneInstance.java` | Lifecycle + phase logic + persistence + render descriptor | Too much storm policy in one object | The renderer can end up reading logic-driven fields directly | Introduce a hurricane snapshot/render boundary later | High | High |
| `client/ClientTickHandler.java` | Fog + audio + particles + sky + culling + tornado updates | One tick hook owns too many unrelated client systems | A future cloud renderer could be debugged in the wrong place | Move toward smaller client coordinators later | High | Medium |
| `client/render/SimpleCloudsTornadoRenderer.java` | Render path + DH routing + depth handling + debug + uniforms | It is already a mini pipeline rather than a simple renderer | Makes renderer bugs hard to isolate from debug behavior | Keep as a reference implementation, then extract a future cloud pipeline boundary | High | High |
| `client/render/SimpleCloudsHurricaneRenderer.java` | Render passes + masks + scratch targets + uniforms | Same issue as the tornado renderer | Hides what is core vs compatibility-specific | Separate pass setup from visual policy later | High | High |
| `client/SimpleCloudsWhiteoutFogHandler.java` | Fog + tint + whiteout + cloud darkening | Fog composition and cloud-related falloff are mixed together | Future cloud shadows may accidentally depend on fog overrides | Move toward a more explicit fog composition boundary later | Medium | Medium |
| `mixin/client/DefaultPipelineTornadoMixin.java` | Render hook + depth policy + fallback logic | A compatibility hook is making core visual decisions | Could confuse where the authoritative render depth path lives | Keep behavior but document it before touching | High | High |
| `mixin/client/DefaultPipelineHurricaneMixin.java` | Render hook + pipeline behavior | Similar to the tornado hook | Can obscure the actual render entry point | Leave in place until renderer boundaries are documented | Medium | High |
