## Cross-Package Ownership Notes

- `api/` and `modules/*`: API contracts are mostly clean; the main risk is broad modules exposing too much live state instead of snapshot contracts.
- `network/` and `client/*`: packet transport is clean, but client packet handlers and caches are broad and should remain separate from core render code.
- `manager/` and `modules/*`: managers coordinate too much and often absorb policy that should belong in module-specific helpers.
- `compat/` and `manager/`: compatibility adapters are currently policy-heavy and should ideally be reduced to adapters.
- `compat/` and `modules/core/`: compatibility code often relies on core value types and should not become the owner of those types.
- `client/` and `network/`: client packet handlers should remain a bridge, not a source of truth.
- `client/` and `client/render/`: client runtime state is still leaking into render helpers; render should consume snapshots, not simulation state.
- `modules/atmosphere/` and `manager/`: atmosphere state is the main source of client-facing weather data, but managers should not become the render boundary.
- `modules/atmosphere/` and `compat/`: compatibility code should not own atmosphere policy.
- `modules/tornado/` and `client/render/`: tornado render state is still split across simulation and renderer; this is a future boundary cleanup area.
- `modules/hurricane/` and `client/render/`: same issue as tornado, especially around render descriptor vs snapshot.
- `util/` and `modules/*`: several utilities are actually orchestration helpers and may eventually deserve more specific packages.
