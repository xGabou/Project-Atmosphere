# Split Or Combine Candidates

| Class or classes | Current problem | Split candidate | Combine candidate | Suggested future structure | Why this helps | Risk | Priority | Should happen before clouds |
|---|---|---|---|---|---|---|---|---|---|
| `AtmosphereManager` | Broad bootstrap and coordination class | Split into bootstrap, sync, regen, and queue coordination | Could combine some thin startup helpers | `AtmosphereBootstrapCoordinator`, `AtmosphereSyncCoordinator`, `AtmosphereRegenCoordinator` later | Makes the source of truth easier to trace | High | High | Yes, at least the documentation should happen first |
| `ForecastOrchestrator` | Handles load/save/regeneration/lookup/sync | Split storage, scheduling, and lookup responsibilities | Could combine with some region lookup helpers | `ForecastRuntimeCoordinator` plus smaller helper services | Clearer forecast ownership for future render snapshots | High | High | Yes |
| `ForecastGenerator` | Does generation, grouping, averaging, fallback assembly | Split pure generation from caching/aggregation | Could combine some generation helpers into one model builder | `ForecastModelBuilder` plus `ForecastAggregation` helper | Prevents the generator from becoming a hidden orchestration layer | High | High | Yes |
| `CloudManager` | Simultaneously applies atmosphere and manages cloud lifecycle | Split state application from spawn/telemetry logic | Could combine with cloud spawning policy if that becomes a separate service | `AtmosphereCloudStateApplier` + `CloudLifecycleController` | Cloud render data becomes easier to source from one place | High | High | Yes |
| `SimpleCloudSpawner` | Weather sampling, selection, search, and telemetry | Split selection policy from spawn search | Could combine with a future cloud catalog or adapter | `CloudSelectionPolicy` + `CloudSpawnSearch` later | Makes Simple Clouds coupling easier to inspect | High | High | Yes |
| `ClientTickHandler` | Too many unrelated client systems | Split fog, audio, particles, culling, and storm visuals | Could combine light-weight client visual helpers | `ClientFogCoordinator`, `ClientVisualEffectsCoordinator` later | Prevents future cloud renderer code from getting buried | High | High | Yes |
| `SimpleCloudsTornadoRenderer` | Mini-pipeline with debug, depth, DH, and uniforms | Split render-pass setup, debug handling, and uniform assembly | Could combine depth helper and shader binding helper | `TornadoRenderPass`, `TornadoRenderDebug`, `TornadoShaderBinding` later | Reduces render-path confusion | High | Medium | Not before fake cloud, but document now |
| `SimpleCloudsHurricaneRenderer` | Similar mini-pipeline problem | Split pass setup, mask generation, and shader parameter assembly | Could combine some shared helper code with tornado renderer later | `HurricaneRenderPass`, `HurricaneMaskPass`, `HurricaneShaderBinding` later | Helps cloud rendering boundaries stay clear | High | Medium | Not before fake cloud, but document now |
| `TornadoInstance` | Simulation and render-adjacent state are mixed | Split render-facing state from simulation state | Could combine with `TornadoSnapshot` in a future read-only layer | `TornadoSimulationState` + `TornadoVisualState` later | Prevents renderer from reading live simulation fields | High | Medium | Later |
| `HurricaneInstance` | Lifecycle, persistence, and render descriptor overlap | Split lifecycle logic from render descriptor data | Could combine with `HurricaneRenderSnapshot` if a read-only model is introduced | `HurricaneSimulationState` + `HurricaneRenderState` later | Clarifies what is authoritative and what is visual | High | Medium | Later |
| `SimpleCloudsWhiteoutFogHandler` | Fog composition and cloud darkening are mixed | Split fog base, whiteout behavior, and cloud tint handling | Could combine with `AtmosphereFogState` if ownership is documented | `FogComposition`, `WhiteoutBlend`, `CloudDarkening` later | Useful before any cloud shadow work | Medium | Medium | Later |
| `WindEngine` and helpers | Many wind model helpers are nearby | Keep split helpers, but document boundaries | Could combine very small math helpers if they are truly local | `WindEngine` plus helper math/model classes | The module is mostly okay; no broad refactor needed yet | Low | Low | No |
